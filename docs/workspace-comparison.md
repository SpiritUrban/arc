# Порівняння ARC Workspace і React Workspace

Базове порівняння виконано на `1d2afd3`, фінальний прогін — на `f98785c`. Висновки стосуються цих реалізацій Workspace і параметрів їхніх збірок. [Підсумок 0.9](#підсумок-09) · [Сценарії паритету](workspace-parity.md) · [Курс 0.9](roadmap-0.9.md)

## Розробка · одне поле через увесь застосунок

У тимчасовому worktree додали необов’язковий **код клієнта** (`reference`, до 24 символів). Він вводиться при створенні та редагуванні, зберігається сервером, відображається в історії й деталях. Один тест для обох стеків перевіряє відмову для 25 символів, шлях `CLIENT-1 → CLIENT-2` через обидві форми та підтвердження значення через REST. Експериментальний код збережено в патчі. [Патч](../tests/workspace-parity/reference-field.patch) · [Відтворення](../tests/workspace-parity/README.md)

| Що змінили | ARC | React + Node |
| --- | --- | --- |
| Вихідний код прикладу, без тесту | 4 файли, +24 / −12 рядків | 4 файли, +13 / −1 рядків |
| Правило довжини | Одна схема поля. Спільний shape підключено до створення, редагування й відповіді. | Одна схема поля. Схема відповіді вже розширювала схему запису. |
| Сервер | Створення вже передає весь input. Редагування явно передає поля до репозиторію. | Створення та редагування вже передають поля зі схеми. Окремий рядок уточнює очищення коду при повній заміні з пропущеним полем. |
| Форми | Нативне іменоване поле потрапляє у вхід мутації без окремого state. Поле й повідомлення додані до двох шаблонів. | Спільний компонент форми додав поле один раз. Потрібні власний state, включення поля в payload і відновлення значення після успіху. |
| Оновлення UI | Наявні ARC `update`-стратегії передають повну підтверджену відповідь у detail і list. | Наявний `saveConfirmedOrder` робить те саме через ключі TanStack Query. |

Менший diff React у цій задачі пояснюється передусім спільним компонентом форми й готовою композицією схеми запису та відповіді. Обидва підходи відділяють доменні обмеження від UI. ARC зменшує ручне з’єднання іменованого поля з мутацією, а React-реалізація локалізує зміну форми в одному компоненті. Розмір diff фіксує саме цей патч. Час розробки не вимірювався.

## Виконання · однаковий локальний сценарій

Node `24.19.0`, Chromium `159.0.8154.6`, production-збірки, loopback HTTP, один тестовий worker, свіжа browser context для кожної спроби. Для кожного застосунку 2 розігрівальні спроби та 10 вимірів. Початкові дані вважаємо готовими після успішних відповідей списків і появи Demo User та порожньої історії. Для submit рахуємо час від події форми до появи нового рядка. Час включає затримку спостереження Playwright. [Сценарій вимірювання](../tests/workspace-parity/comparison.spec.mjs)

| Показник | ARC | React + Node |
| --- | ---: | ---: |
| JS, завантажений до початкових даних на `/orders` | 131 899 байтів, 4 запити | 375 549 байтів, 1 запит |
| До початкових даних, медіана / p90 | 247,9 / 335,8 мс | 289,5 / 309,2 мс |
| Submit → новий рядок, медіана / p90 | 61,7 / 105,4 мс | 46,9 / 71,0 мс |
| Читання під час редагування | 0 | 0 |
| Фонове читання при поверненні до прогрітого списку | 0 | 1 |

Обидва локальні сервери віддали JS без стиснення. ARC завантажив менше JS і досяг початкових даних швидше за медіаною в цьому прогоні, React мав менший p90 старту й швидше показав новий рядок після submit. Один серійний прогін на loopback задає вихідні числа для повторної перевірки. Пізніший профіль submit наведено нижче.

## Діагностика · конфлікт після скасування в іншій вкладці

Після завантаження історії тест скасовує замовлення через REST, а потім натискає «Скасувати» в браузері зі старими даними. Обидві реалізації повертають HTTP 409 з `ORDER_ALREADY_CANCELLED` і показують повідомлення біля рядка. Рядок в обох випадках лишається зі статусом «Створено».

У React-збірці браузерна мережа дає URL, HTTP-статус і код помилки. Для зв’язування цього кліку з конкретним серверним кроком знадобилася б додаткова телеметрія. ARC Stand за trace ID відповіді показав подію прив’язки, action і remote call, а також операцію `orders.cancel`, визначення користувача й виклик `orders.repository.cancel`. У цьому сценарії причина збою видима в одній взаємодії без додаткової інструментації прикладу. [Наскрізна траса ARC](fullstack/tracing.md)

Next.js App Router дає інтегровані файлові маршрути, layout і серверний рендеринг. Це корисний орієнтир для навігації та інтеграції fullstack, а наведені виміри виконано для клієнтських маршрутів React Router і окремого Node API. [Next.js App Router](https://nextjs.org/docs/app)

## Прогрес після базового порівняння

ARC Workspace застосовує підтверджене замовлення з details відповіді 409. Спільний браузерний прогін підтверджує статус «Скасовано» і повідомлення про конфлікт у списку й деталях ARC, з 0 додаткових читань. Базові виміри вище збережено для повторного порівняння після серії виправлень.

Після виділення `OrderFields` повторили експеримент із `reference`. В ARC поле та повідомлення тепер оголошуються в одному TSX-компоненті, а тип поля підтягується зі схеми. Diff ARC для експерименту змінився з 4 файлів, +24 / −12 рядків на 5 файлів, +19 / −12. Новий файл у diff відображає винесений компонент. React лишився на 4 файлах, +13 / −1. Обидві реалізації пройшли той самий браузерний сценарій створення, редагування й валідації нового поля. [Патч повторного експерименту](../tests/workspace-parity/reference-field-shared-form.patch)

## Профіль створення замовлення

На базі `7bcb6b9` повторили прогін із точнішою часовою межею. Мітка ставиться в capture-фазі submit, а `MutationObserver` фіксує появу рядка. HTTP-фази беруться з Playwright після завершення відповідей. Окремий прогін затримує доставку кожної відповіді ARC і React на 40 мс через Playwright. Він включає накладні витрати перехоплення й моделює дві послідовні затримки. У кожному режимі 10 вимірів після двох розігрівальних спроб на застосунок. [Сценарій прогону](../tests/workspace-parity/comparison.spec.mjs) · [Playwright Request Timing](https://playwright.dev/docs/api/class-request#request-timing)

| Фаза, мс | ARC, loopback | React, loopback | ARC, +40 мс | React, +40 мс |
| --- | ---: | ---: | ---: | ---: |
| Submit → HTTP-запис | 2,4 | 3,9 | 2,6 | 3,9 |
| HTTP-запис | 2,6 | 2,2 | 70,0 | 52,3 |
| Відповідь запису → HTTP-читання | 8,1 | 9,1 | 3,2 | 3,6 |
| HTTP-читання списку | 8,5 | 3,9 | 65,4 | 50,9 |
| Відповідь читання → новий рядок | 5,3 | 4,1 | 2,7 | 3,2 |
| Submit → новий рядок, медіана / p90 | 27,9 / 51,3 | 23,4 / 26,6 | 144,7 / 179,2 | 114,2 / 117,9 |

Фази в таблиці — окремі медіани. Stand показав медіани серверних операцій ARC близько 0,20 мс для створення й 0,19 мс для читання. Обидва стеки зробили рівно один запис і одне читання у всіх вимірах. Найбільша різниця на loopback припала на читання списку, а в контрольованому прогоні з затримкою обидві відповіді домінували над часом до появи рядка. У цьому сценарії найбільший доступний резерв ARC — прибрати повторне читання за наявності повного кешованого списку й застосувати до нього підтверджений рядок. Після зміни треба повторити вимір і окремо перевірити холодний кеш та запізнілі відповіді.

## Створення з оновленням кешу ARC

ARC застосовує підтверджене замовлення через `ordersData.insertBy("id")`. Стратегія оновлює завантажений список власника, від імені якого надіслано форму. Якщо читання вже триває, вставка також застосовується до його результату й зберігає наявний рядок із тим самим ID. У Chromium три окремі перевірки підтвердили обидва порядки відповіді першого читання та оновлення кешу початкового власника після перемикання. [Перевірки в Chromium](workspace-parity.md#спільний-прогін-у-chromium)

Профіль повторили в Chromium `159.0.8154.6` і Node `24.19.0` за тією самою методикою з двома розігрівальними спробами й десятьма вимірами на застосунок у кожному режимі. Час від submit до нового рядка наведено в мілісекундах. [Команди прогону](../tests/workspace-parity/README.md#порівняльний-прогін)

| Реалізація | Записи / читання після submit | Loopback, медіана / p90 | +40 мс на відповідь, медіана / p90 |
| --- | ---: | ---: | ---: |
| ARC до зміни | 1 / 1 | 27,9 / 51,3 | 144,7 / 179,2 |
| ARC з оновленням кешу | 1 / 0 | 15,8 / 19,0 | 81,8 / 110,3 |
| React у повторному прогоні | 1 / 1 | 23,3 / 35,6 | 112,0 / 115,6 |

У повторному прогоні ARC перейшов від відповіді запису до нового рядка за 10,7 мс за медіаною на loopback. У режимі із затримкою до ARC застосовано одну затримку доставки, а до React — дві. Результати описують створення замовлення після повного завантаження списку в цих збірках.

## Скільки коду вимагає форма

Порівнюємо конкретні форми Workspace за тим, що автор має виразити в коді для тієї самої поведінки. HTML-розмітка, тексти помилок і правила предметної області потрібні в обох реалізаціях.

| Задача автора | ARC Workspace | React Workspace |
| --- | --- | --- |
| Зібрати й перевірити значення | `name` на полях та `onSubmit={createOrder}`. ARC читає форму й застосовує контракт. | Стан полів, `onChange`, обробник submit, перетворення кількості й `safeParse`. |
| Передати ID для редагування | Сторінкова `mutation` додає ID маршруту до даних форми. | Функція мутації бере `order.id` із замикання. |
| Обробити pending і скинути форму | ARC вимикає submit і відновлює початкові значення. Шаблон визначає текст кнопки та повідомлення. | Код пов’язує стан мутації з кнопкою та іменованим ключем, перевіряє повторне надсилання і відновлює значення після відповіді. |
| Оновити список і деталі | `update: [order.replace(), ordersData.replaceBy("id")]` оголошує дві цілі. | `onSuccess` викликає `saveConfirmedOrder`, який оновлює дві цілі через ключі TanStack Query. |

Це порівняння реалізацій у репозиторії. React також підтримує нативні неконтрольовані поля. Перевага ARC у цьому прикладі полягає в тому, що той самий контракт уже пов’язує іменовані поля, валідацію, відправлення й оновлення кешу.

Після замірів спростили API для одного відомого конфлікту. У базовій реалізації ARC сторінка передавала мутацію й цілі в `cancelAndReconcile`. Ця функція захоплювала ключі кешу, переносила trace ID і застосовувала відповідь у batch. Тепер `updateOnError: "ORDER_ALREADY_CANCELLED"` повторно використовує цілі з `update`. Код дії викликає мутацію, а повідомлення про конфлікт читається через `failed(...)`. React Workspace показує повідомлення після `409` і залишає старий статус рядка, тож довжина його обробника тут відображає іншу поведінку. [Форма ARC](../examples/workspace/pages/orders/%5Bid%5D.tsx) · [Мутації React](../examples/react-workspace/src/orders/actions.tsx)

У деталях ARC скасування теж використовує `onSubmit={cancelOrder}`. Єдиний параметр береться з маршруту, а шаблон містить форму з кнопкою та її підписом. Блокування повторного submit діє так само, як під час редагування. У списку, де одночасно можуть виконуватися дії для різних рядків, лишається `cancelOrder.run({ id: order.id })` з дедуплікацією за ключем.

React Workspace читає `query.data` один раз під час рендерингу й далі працює зі звичайним об’єктом. Тепер зведення ARC робить те саме всередині реактивної ділянки `{renderSummary(order.data())}`. Функція один раз перевіряє, чи запис існує, і нижче читає `saved.product`, `saved.quantity` та `saved.total` напряму. Сторінка окремо читає `order.loading()` і `order.error()`, а редактор отримує реактивне `order.data`. Це використовує наявні API query й TSX. [Деталі ARC](../examples/workspace/pages/orders/%5Bid%5D.tsx) · [Деталі React](../examples/react-workspace/src/orders/detail.tsx)

У списку React нормалізує пошук і фільтрує замовлення в `orderHistory(...)` під час рендерингу компонента. ARC раніше викликав фільтрацію окремо для таблиці й перевірки порожнього списку, а умову активного фільтра повторював у заголовку та поясненні. Тепер ці прив’язки читають `history().rows` і `history().filtering` зі спільного обчислення. У React для цього достатньо виклику звичайної функції. У шаблоні ARC викликає `derive([visibleOrders, search, status], compute)`. ARC формує ID для графа та звільняє обчислення разом із view. Шаблон у `view({ state, template })` отримує типи сигналів із початкового стану. Кожне поле пошуку й статусу в ARC використовує один `bind:value`. [Список ARC](../examples/workspace/orders/page.tsx) · [Список React](../examples/react-workspace/src/orders/panel.tsx)

У React кожна кнопка скасування створює `useMutation` і використовує окремий ключ у `useIsMutating` та перевірці повторного кліку. В ARC усі рядки використовують спільну мутацію з `key: "id"`. Компонент кнопки прив’язує вхід через `cancelOrder.for({ id })` і використовує `run`, `pending()` та `outcome()` однієї прив’язки. [Рядок ARC](../examples/workspace/orders/page.tsx) · [Кнопка React](../examples/react-workspace/src/orders/actions.tsx)

Створення й редагування профілю тепер використовують один `ProfileForm` в обох реалізаціях. ARC обирає мутацію в `onSubmit`, читає іменовані поля й сам блокує кнопку під час запиту. ARC передає ID редагованого профілю через `updateUser.with({ id: user.id })`, React передає його через замикання. Playwright перевіряє, що перемикання користувача під час запиту зберігає зміну для початкового профілю. [Профіль ARC](../examples/workspace/users/page.tsx) · [Профіль React](../examples/react-workspace/src/users/panel.tsx)

Після створення профілю ARC додає підтверджений запис через `update: users.insertBy("id")`, а React Workspace викликає `invalidateQueries`. У сценарії з уже завантаженим списком від надсилання форми до появи вибраного профілю ARC зробив 0 повторних читань списку, React зробив 1. [Браузерна перевірка](../tests/workspace-parity/workspace.spec.mjs)

Після редагування ARC замінює запис через `update: users.replaceBy("id")`, а React Workspace замінює його через `setQueryData`. У браузерному сценарії обидві реалізації показали підтверджені ім’я та email у списку без повторного читання. [Сценарій USR-01–03](../tests/workspace-parity/workspace.spec.mjs)
