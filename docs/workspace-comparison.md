# Порівняння ARC Workspace і React Workspace

Ітерація 7 курсу 0.9. База вимірювання — `1d2afd3`, на якій обидві реалізації пройшли спільні сценарії в Chromium. Висновки стосуються цих реалізацій Workspace і поточних параметрів збірки. [Сценарії паритету](workspace-parity.md) · [Курс 0.9](roadmap-0.9.md)

## Розробка · одне поле через увесь застосунок

У тимчасовому worktree додали необов’язковий **код клієнта** (`reference`, до 24 символів). Він вводиться при створенні та редагуванні, зберігається сервером, відображається в історії й деталях. Один тест для обох стеків перевіряє відмову для 25 символів, шлях `CLIENT-1 → CLIENT-2` через обидві форми та підтвердження значення через REST. Експериментальний код збережено в патчі. [Патч](../tests/workspace-parity/reference-field.patch) · [Відтворення](../tests/workspace-parity/README.md)

| Що змінили | ARC | React + Node |
| --- | --- | --- |
| Вихідний код прикладу, без тесту | 4 файли, +24 / −12 рядків | 4 файли, +13 / −1 рядків |
| Правило довжини | Одна схема поля. Спільний shape підключено до створення, редагування й відповіді. | Одна схема поля. Схема відповіді вже розширювала схему запису. |
| Сервер | Створення вже передає весь input. Редагування явно передає поля до репозиторію. | Створення та редагування вже передають поля зі схеми. Окремий рядок уточнює очищення коду при повній заміні з пропущеним полем. |
| Форми | Нативне іменоване поле потрапляє у вхід мутації без окремого state. Поле й повідомлення додані до двох шаблонів. | Спільний компонент форми додав поле один раз. Потрібні власний state, включення поля в payload і відновлення значення після успіху. |
| Оновлення UI | Наявні ARC `update`-стратегії передають повну підтверджену відповідь у detail і list. | Наявний `saveConfirmedOrder` робить те саме через ключі TanStack Query. |

Менший diff React у цій задачі пояснюється передусім спільним компонентом форми й готовою композицією схеми запису та відповіді. Обидва підходи відділяють доменні обмеження від UI. ARC зменшує ручне з’єднання іменованого поля з мутацією, а React-реалізація локалізує зміну форми в одному компоненті. Розмір diff фіксує саме цей патч. Час розробки не вимірювався.

## Виконання · однаковий локальний сценарій

Node `24.19.0`, Chromium `159.0.8154.6`, production-збірки, loopback HTTP, один тестовий worker, свіжа browser context для кожної спроби. Для кожного застосунку 2 розігрівальні спроби та 10 вимірів. Початкові дані вважаємо готовими після успішних відповідей списків і появи Demo User та порожньої історії. Для submit рахуємо час від події форми до появи нового рядка. Час включає затримку спостереження Playwright. [Сценарій вимірювання](../tests/workspace-parity/comparison.spec.mjs)

| Показник | ARC | React + Node |
| --- | ---: | ---: |
| JS, завантажений до початкових даних на `/orders` | 131 899 байтів, 4 запити | 375 549 байтів, 1 запит |
| До початкових даних, медіана / p90 | 247,9 / 335,8 мс | 289,5 / 309,2 мс |
| Submit → новий рядок, медіана / p90 | 61,7 / 105,4 мс | 46,9 / 71,0 мс |
| Читання під час редагування | 0 | 0 |
| Фонове читання при поверненні до прогрітого списку | 0 | 1 |

Обидва локальні сервери віддали JS без стиснення. ARC завантажив менше JS і досяг початкових даних швидше за медіаною в цьому прогоні, React мав менший p90 старту й швидше показав новий рядок після submit. Один серійний прогін на loopback задає вихідні числа для повторної перевірки. Профілювання повільнішого submit і виміри на мережі з затримкою залишаються окремими задачами.

## Діагностика · конфлікт після скасування в іншій вкладці

Після завантаження історії тест скасовує замовлення через REST, а потім натискає «Скасувати» в браузері зі старими даними. Обидві реалізації повертають HTTP 409 з `ORDER_ALREADY_CANCELLED` і показують повідомлення біля рядка. Рядок в обох випадках лишається зі статусом «Створено».

У React-збірці браузерна мережа дає URL, HTTP-статус і код помилки. Для зв’язування цього кліку з конкретним серверним кроком знадобилася б додаткова телеметрія. ARC Stand за trace ID відповіді показав подію прив’язки, action і remote call, а також операцію `orders.cancel`, визначення користувача й виклик `orders.repository.cancel`. У цьому сценарії причина збою видима в одній взаємодії без додаткової інструментації прикладу. [Наскрізна траса ARC](fullstack/tracing.md)

Next.js App Router дає інтегровані файлові маршрути, layout і серверний рендеринг. Це корисний орієнтир для навігації та інтеграції fullstack, а наведені виміри виконано для клієнтських маршрутів React Router і окремого Node API. [Next.js App Router](https://nextjs.org/docs/app)

## Прогрес після базового порівняння

ARC Workspace застосовує підтверджене замовлення з details відповіді 409. Спільний браузерний прогін підтверджує статус «Скасовано» і повідомлення про конфлікт у списку й деталях ARC, з 0 додаткових читань. Базові виміри вище збережено для повторного порівняння після серії виправлень.

## Розриви для окремих ітерацій

1. **Звіряти стан після відомого конфлікту.** Почати з `ORDER_ALREADY_CANCELLED`. Після 409 ARC має зберегти зрозумілий зворотний зв’язок і показати підтверджений сервером статус у списку та деталях. Додати браузерну перевірку і виміряти читання. Перевірити, чи достатньо поточного mutation API, перш ніж розширювати його.
2. **Зменшити дублювання полів створення та редагування.** Перевірити спільну TSX-композицію на одному полі, зберегти нативний submit, польові помилки, життєвий цикл і видимість у графі. Повторити експеримент на меншому diff.
3. **Профілювати submit.** Розкласти час на HTTP, обробку контракту, refresh і DOM update. Змінювати виконання лише після повторного виміру, який підтвердить конкретне вузьке місце.
