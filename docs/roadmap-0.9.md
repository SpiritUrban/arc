# Курс ARC 0.9

Відтворити функціональність [ARC Workspace](workspace-app.md) на React, порівняти обидві реалізації на однакових задачах і використати результати для конкретних поліпшень ARC. База ARC для першого порівняння — локальна контрольна точка `v0.8.0`.

## Вибір React-стеку

Основний варіант — **React + TypeScript + Vite + React Router у браузері, окремий HTTP API на Node.js**. Для кешу запитів і мутацій використовуємо TanStack Query, для спільних схем — Zod. Точні версії зафіксуємо під час створення застосунку. У dev клієнт ходить до API через проксі, а зібрані assets і API доступні через один origin.

Це найближчий варіант за моделлю виконання. ARC Workspace має клієнтські маршрути, інтерактивні форми, клієнтський кеш і явну HTTP-межу з Node. В обох реалізаціях можна перевірити той самий шлях від форми через HTTP до відповіді та оновлення кешу. React-реалізація використовує власний сервер і власні схеми, щоб у порівняння ввійшли також контракти, валідація та зв’язування з UI. [Створення застосунку React](https://react.dev/learn/creating-a-react-app) · [Архітектура Workspace](workspace-app.md)

Next.js App Router ближчий до ARC за файловими сторінками, вкладеними layout і спільним запуском frontend та backend. Його серверний рендеринг, Server Components і Server Functions додають іншу модель виконання. Порівняємо ці можливості якісно в підсумку. Другий повний порт на Next.js знадобиться лише окремим рішенням, якщо питання після порівняння стосуватиметься саме цієї моделі. [Next.js App Router](https://nextjs.org/docs/app) · [Server та Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)

## Правила порівняння

- Фіксуємо однакові дані, доменні правила, екрани, маршрути й очікування від UI. Для обох реалізацій використовуємо спільні сценарії приймання. Для порівняння достатня функціональна й візуальна відповідність Workspace.
- По можливості повторно використовуємо стилі та нейтральні fixtures. Окремо реалізуємо серверні операції, схеми, клієнтські запити й мутації. Підрахунок коду відокремлює доменну логіку, інтеграційний код, конфігурацію й тести.
- Кожен пункт у послідовності — окрема ітерація. Ітерація має перевірний результат. Після перевірки записуємо результат у цей документ і одразу комітимо. Якщо порівняння породжує кілька змін ARC, кожну перевіряємо й комітимо окремо.
- Для вимірювань використовуємо збірки для запуску, однакові браузер, Node, дані та умови мережі. Фіксуємо версії, команди й повторюваність. Швидкість розробки оцінюємо на однаковій зміні з перевірним diff.
- ARC 0.9 лишається внутрішньою контрольною точкою розробки.

## Послідовність ітерацій

### 1. Зафіксувати поведінку Workspace

Звірити код, посібник і тести ARC Workspace. Спільні сценарії, початкові дані та запуск зафіксовано в [таблиці паритету Workspace](workspace-parity.md).

### 2. Запустити каркас React Workspace

Створити окремий runnable-приклад поруч із ARC Workspace. Підключити React, маршрути `/`, `/orders`, `/orders/:id`, спільний layout і Node HTTP API. Перевірити dev і build/start, прямий вхід на detail route та browser/server межу в збірці.

### 3. Відтворити користувачів

Перенести початкового Demo User, пошук, вибір, створення та редагування профілю. Перевірити валідацію, duplicate email, pending, збереження введених значень після помилки й автовибір нового користувача.

### 4. Відтворити створення й історію замовлень

Перенести контракт створення, розрахунок суми, серверну перевірку власника, список і підсумки за користувачем. Перевірити фільтри за товаром і статусом, незмінність загальних підсумків за фільтрації, перемикання власника під час читання та повернення до кешованого списку.

### 5. Відтворити деталі, редагування й скасування замовлень

Перевірити пряме посилання на detail, доступ за власником, оновлення detail і list після редагування або скасування, заборону редагування скасованого замовлення та незалежні pending/error стани дій за рядками. Зафіксувати, коли використано відповідь мутації й скільки повторних запитів це потребує.

### 6. Підтвердити функціональний паритет

Прогнати обидві реалізації за спільними сценаріями на реальному браузері. Для гонок і pending керувати порядком HTTP-відповідей. Перевірити loading, empty і error states, навігацію, помилки біля полів, порядок оновлення даних, захист межі власника та відсутність серверного коду в клієнтському bundle.

### 7. Порівняти розробку, виконання та діагностику

На обох реалізаціях виконати однакову невелику зміну, наприклад додати поле замовлення через схему, API, форму й відображення. Порівняти кількість місць зміни та дублювання правил, ясність типів і помилок, навігацію, кеш, мережеві запити й зусилля для діагностики одного збою. Зафіксувати розмір завантаженого JS та час до початкових даних і до оновлення UI після submit. Для діагностики використати ARC Stand та звичні браузерні й серверні інструменти React-стеку. Результат — таблиця плюсів, мінусів і відтворюваних розривів.

### 8. Усунути підтверджені розриви в ARC

Для кожного розриву визначити очікувану поведінку, тест і мінімальну зміну в ARC. Починати з коректності UX і контрактів, далі брати суттєві незручності розробки або виміряні регресії. Кожне виправлення є окремою ітерацією з повторним прогоном відповідного сценарію та власним комітом.

### 9. Повторити порівняння й зафіксувати результат 0.9

Повторити сценарії та вимірювання після змін. Показати, де ARC досяг паритету, де має перевагу й де лишається компроміс. Зафіксувати перевірені висновки, посилання на коміти й актуальні інструкції запуску обох застосунків.

## Критерії успіху

- React Workspace самостійно запускається й відтворює погоджені сценарії ARC Workspace.
- Обидві реалізації проходять спільні перевірки поведінки. Критичні проблеми доступу, гонок, валідації чи неузгоджених даних мають відтворення.
- Для кожної заявленої переваги або недоліку є приклад коду, сценарій або вимірювання. Результати стосуються цих реалізацій Workspace.
- ARC досягає щонайменше функціонального паритету на погоджених сценаріях. Для пріоритетних розривів задокументовано виправлення й повторну перевірку, а для решти — конкретний компроміс і його наслідки.

## Прогрес

**Ітерацію 1 виконано.** [Таблиця паритету](workspace-parity.md) фіксує чистий старт, спільний набір даних, сценарії й рівень покриття ARC на `v0.8.0`.

**Ітерацію 2 виконано.** [React Workspace](../examples/react-workspace/README.md) має власний lockfile, три маршрути, спільний layout і Node API під `/api`. Vite проксіює API в dev, а Node віддає API й клієнтську збірку з одного origin після build. Перевірено HTTP-вхід на три маршрути, зокрема прямий вхід на detail, видачу assets, API, 404 у зібраному застосунку та відсутність серверних імпортів у клієнтській збірці. Пройшли типізація ARC, збірка React Workspace й npm audit.

**Ітерацію 3 виконано.** React Workspace має Demo User, пошук, спільний вибір користувача, форми створення й редагування та Node API. Спільні Zod-схеми перевіряють профіль на обох боках. Створення вибирає новий запис і повторно читає список, редагування оновлює кеш із підтвердженої відповіді. У dev і зі збірки перевірено створення, читання, редагування та відмови для невалідних полів, дубліката email й відсутнього запису. Типізація та збірка пройшли. Браузерний прогін USR-01–03 лишається в ітерації паритету.

**Ітерацію 4 виконано.** React Workspace створює й читає замовлення за активним власником. Node визначає власника за Bearer UUID та обчислює суму. Історія фільтрується за товаром і статусом, а підсумки рахуються за всіма замовленнями власника. У dev і зі збірки перевірено API, ізоляцію двох користувачів, підсумки 3 / 150 ₴ і комбіновані фільтри. Перевірка TanStack Query підтвердила скасування попереднього читання, відсутність чужого snapshot після перемикання та кешоване повернення з фоновим оновленням. Для фільтра статусу перевірка використовувала fixture зі скасованим рядком. Браузерний прогін лишається в ітерації паритету.

**Ітерацію 5 виконано.** React Workspace відкриває деталі за прямим URL, редагує та скасовує замовлення. У dev і зі збірки перевірено перевірку власника для всіх трьох операцій, перерахунок суми, дві паралельні дії на різних рядках і відмову після скасування. Підтверджені відповіді оновили detail і list без додаткових GET під час мутацій. Читання при навігації та pending/error у DOM ще треба виміряти в браузері. Типізація та збірка пройшли.

**Ітерацію 6 виконано.** Спільний набір Playwright прогнав обидві збірки в Chromium. Пройшли 8 із 8 перевірок, по чотири на ARC і React. Поведінка збігається в перевірених сценаріях, а відмінності в перевірці email та повторному читанні після навігації зафіксовано в [таблиці паритету](workspace-parity.md). [Команди прогону](../tests/workspace-parity/README.md)

**Ітерацію 7 виконано.** [Порівняння Workspace](workspace-comparison.md) містить спільний експеримент із полем замовлення, виміри запуску й submit та діагностику HTTP 409. Playwright перевірив обидві реалізації експерименту. У локальному прогоні ARC завантажив менше JS, React швидше показав новий рядок після submit. Обидві реалізації лишили застарілий статус після конфлікту, а ARC Stand показав причину в наскрізній трасі.

**Перше виправлення за результатами порівняння — узгодження статусу після конфлікту скасування.** ARC Workspace отримує підтверджене замовлення в типізованих details відповіді `ORDER_ALREADY_CANCELLED`. Наявні стратегії оновлення query застосовують його до ключа початкового власника без додаткового читання. Список і деталі показують «Скасовано» та зберігають повідомлення про конфлікт. Перевірки покривають перемикання власника під час відповіді й спільний trace ID для мутації та оновлення списку.

**Спільні TSX-поля — перевірено.** Створення та редагування замовлення використовують один `OrderFields`. Типи імен полів і даних виводяться з контракту. В обох формах збережено нативний submit, польові помилки й реактивні значення. Семантичний тест перевіряє прив’язки мутацій у графі. В експерименті `reference` тепер додається до одного шаблону полів, а diff ARC скоротився з +24 / −12 до +19 / −12 рядків. [Порівняння й повторний патч](workspace-comparison.md)

**Submit створення — профіль знято.** У Chromium зафіксовано п’ять фаз від події форми до нового рядка, зі звіркою серверних операцій ARC у Stand. Обидві реалізації роблять запис і повторне читання. У контрольованому прогоні з затримкою читання ARC займало 65,4 мс за медіаною, тоді як серверна операція читання — близько 0,19 мс. Пройшли обидва проєкти в кожному з двох режимів. [Профіль і методика](workspace-comparison.md#профіль-створення-замовлення)

**Оновлення кешу після створення — виконано.** ARC додає підтверджений рядок за ID до списку початкового власника. Браузерний прогін підтвердив дедуплікацію, перше читання списку та зміну власника під час submit. Після завантаження списку створення виконує один HTTP-запис без повторного читання. Медіана до появи рядка зменшилася з 27,9 до 15,8 мс на loopback і зі 144,7 до 81,8 мс із контрольованою затримкою. [Повторний профіль](workspace-comparison.md#створення-з-оновленням-кешу-arc)

**Ітерації 8 і 9 виконано.** Три пріоритетні розриви перевірено після змін окремими сценаріями. Фінальний прогін підтвердив функціональну відповідність погоджених сценаріїв і зафіксував відмінності у старті, створенні, діагностиці конфлікту та розмірі зміни форми. [Підсумок 0.9, коміти та запуск](workspace-comparison.md#підсумок-09)

## Висновки 0.9.0 і подальший розвиток

Workspace показав, де ARC найкраще зменшує кількість рішень у коді застосунку. Схема визначає поля й обмеження, контракт описує бізнес-помилку, мутація задає цілі оновлення, а компонент відображає дані й підключає дію. Наприклад, сторінка деталей отримує ID із маршруту, використовує ті самі поля, що й форма створення, та оголошує спільні цілі оновлення для редагування й скасування. Репозиторій перевіряє власника й допустимість зміни замовлення під час запису. [Деталі замовлення](../examples/workspace/pages/orders/%5Bid%5D.tsx) · [Контракти](../examples/workspace/orders/contracts.ts)

Найвідчутніша зміна поведінки — застосування підтвердженої відповіді до кешу. Після завантаження списку для створення замовлення достатньо одного HTTP-запису. За конфлікту скасування список і деталі отримують актуальне замовлення, а користувач бачить повідомлення про конфлікт. Порівняння з React дало відтворювані сценарії й показники саме для Workspace. Його варто зберегти як контрольну перевірку при змінах поведінки. [Результати порівняння](workspace-comparison.md#підсумок-09)

Наступний етап має закріпити основний спосіб роботи з API й перевірити його на складнішому сценарії.

1. **Закріпити основний спосіб роботи з API.** На наскрізному прикладі показати, як обрати між `refresh` і `update`, коли автоматичного ключа достатньо і коли потрібен явний. Окремо зафіксувати, яку поведінку зберігають підтримувані форми виклику. Нові скорочення мають прибирати повторене рішення у сценарії.
2. **Перевірити модель даних у другому сценарії.** Взяти список із серверною фільтрацією або пагінацією, де одного запису у відповіді може бути замало для оновлення всього результату. Перевірити зміну ключа під час запису, паралельні відповіді й узгодження між списком та деталями. За результатом вирішити, чи достатньо наявних `refresh` і `update`.
3. **Стабілізувати межі контракту й діагностику.** Тримати однакове декодування параметрів у HTTP, браузері та Stand. Перевіряти, що помилка поля, конфлікт, серверна операція й оновлення запиту простежуються від події до результату. Зміни поведінки на цих межах фіксувати в нотатках міграції.
