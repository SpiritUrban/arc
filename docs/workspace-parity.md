# Workspace · сценарії паритету ARC і React

База порівняння — `v0.8.0` (`f513506`). Еталонна поведінка визначена кодом [ARC Workspace](../examples/workspace/app.ts). Ця таблиця задає спільні сценарії приймання для ARC і React Workspace. Колонка «Покриття ARC» описує наявні докази для цієї бази. Реальний браузер перевірятимемо окремо на обох застосунках. [Посібник Workspace](workspace-app.md) · [Інтеграційні тести](../tests/workspace.test.ts)

## Запуск ARC

```sh
npm ci
PORT=4323 STAND_PORT=4324 npm run dev:workspace
```

Застосунок доступний на `http://localhost:4323`, Stand — на `http://localhost:4324`. Для перевірки збірки виконати `npm run build`, для прогону тестів Workspace — `node --conditions=arc-source --import tsx --test tests/workspace.test.ts`. Тести Workspace запускають локальний HTTP і використовують LinkeDOM та VM. Каркас React запускається через `npm ci && npm run dev` у каталозі прикладу. [Команди React Workspace](../examples/react-workspace/README.md)

## Початкові дані

Обидві реалізації після старту мають одного активного користувача **Demo User** (`demo@example.com`, UUID `00000000-0000-4000-8000-000000000001`) і порожню історію замовлень. Дані зберігаються в пам’яті процесу. Для незалежного сценарію перезапустити застосунок або явно почати з чистого сховища. [Початковий користувач](../examples/workspace/users/server.ts) · [Сховище замовлень](../examples/workspace/orders/server.ts)

Для сценаріїв з кількома записами створити **Olena Test** (`olena@example.com`) і від її імені створити наведені нижче замовлення в такому порядку. «Папір» після створення скасувати. Для перевірки доступу створити від імені Demo User окреме замовлення «Маркер» кількістю 1. ID брати з відповідей створення або зі сторінки. UUID і точні тексти технічних помилок можуть різнитися, значущі коди доменних помилок і поведінка UI мають збігатися.

| Власник | Товар | Кількість | Сума | Статус |
| --- | --- | ---: | ---: | --- |
| Olena Test | ARC Блокнот | 2 | 50 ₴ | Створено |
| Olena Test | Блокнот А5 | 3 | 75 ₴ | Створено |
| Olena Test | Папір | 1 | 25 ₴ | Скасовано |
| Demo User | Маркер | 1 | 25 ₴ | Створено |

Загальні підсумки Olena перед фільтрацією й після неї — 3 замовлення і 150 ₴, включно зі скасованим. Роль вибирається в UI. Сервер визначає власника замовлень за Bearer UUID вибраного користувача. Це демонстраційна модель ідентичності. [Підсумки й фільтри](../examples/workspace/orders/page.tsx) · [Визначення власника](../examples/workspace/auth.ts)

## Спільні сценарії

| ID | Дія й очікування | Покриття ARC |
| --- | --- | --- |
| NAV-01 | Відкрити `/`, `/orders`, пряме посилання `/orders/:id`. Є спільна навігація й правильний активний пункт. Ідентифікатор з URL використовується для читання деталей. Невідомий маршрут повертає 404. | HTTP і LinkeDOM. Реальна навігація та back/forward ще не перевірені. |
| USR-01 | Першим бачимо Demo User. Пошук за ім’ям або email звужує список. Вибір змінює активного користувача й область даних замовлень. | LinkeDOM. Пошук за email і вибір покриті, пошук за ім’ям звірено з кодом. |
| USR-02 | Створити Olena. Під час запиту показано pending. Після успіху форма очищається, Olena з’являється в списку й стає активною. Ім’я коротше 2 символів і некоректний email відхиляються. При дублікаті email показано польову помилку, значення збережені. | LinkeDOM покриває успіх, pending, коротке ім’я та дублікат. Некоректний формат email звірено зі схемою. |
| USR-03 | Змінити ім’я та email вибраного користувача. Список і картка активного користувача показують підтверджені значення. Дублікат email відхиляється, попередні збережені дані лишаються. | Код і зафіксована ручна перевірка успіху в [курсі 0.7](roadmap-0.7.md). Повний сценарій ще треба автоматизувати. |
| ORD-01 | Створити замовлення для активного користувача. `2 × 25` дає 50 ₴. Після успіху список і підсумки оновлюються, форма повертається до початкових значень. Порожній товар та кількість поза 1–100 дають польові помилки без нового замовлення. | LinkeDOM і HTTP. Верхню межу, нецілі числа та довжину назви звірено зі схемою. |
| ORD-02 | В історії Olena фільтр «блокнот» показує два рядки. Фільтр «Скасовано» без пошуку показує «Папір». Разом вони дають порожній результат. Підсумки лишаються 3 і 150 ₴. Окремо перевірити повідомлення для порожньої історії та відсутності збігів. | Код і зафіксована ручна перевірка фільтрів у [курсі 0.7](roadmap-0.7.md). |
| ORD-03 | Затримати відповідь історії Olena й переключитися на Demo. Історія Olena одразу зникає. Пізня відповідь не підміняє історію Demo. Після повернення до Olena її кешований список видно під час фонового оновлення. | Кешоване повернення та ізоляція покриті в Workspace. Пізні відповіді покриті [тестами ресурсів](../tests/web-async.test.ts). |
| ORD-04 | Відкрити замовлення Olena під її ідентичністю. Під Demo або для невідомого ID отримати відмову, без даних чужого замовлення. Перевірити читання, редагування й скасування іншого власника; без відомої ідентичності операції замовлень повертають 401. | HTTP і LinkeDOM покривають читання та відмову для чужого скасування. Інші відмови звірено з серверним кодом. |
| ORD-05 | Змінити «ARC Блокнот» на «Робочий блокнот» і кількість на 4. Деталі показують 100 ₴, історія показує підтверджені товар і кількість, загальна сума Olena стає 200 ₴. Зафіксувати кількість читань під час submit і після повернення до історії окремо. | LinkeDOM перевіряє submit, оновлення detail та події зміни detail/list. Повернення до історії перевірялося вручну. |
| ORD-06 | Скасувати замовлення зі списку й окремо зі сторінки деталей. На час запиту pending стосується вибраного рядка, повторний клік не дублює ту саму дію. Після успіху detail і list показують «Скасовано». Повторне скасування дає 409, скасоване замовлення не можна редагувати. | LinkeDOM і HTTP покривають список, незалежність дій за рядками й повторне скасування. Detail перевірявся вручну. |
| BUILD-01 | У зібраному застосунку HTML і клієнтські assets віддаються з того самого origin, звідки викликається API. Схеми доступні клієнту, сховища та серверна реалізація авторизації не потрапляють у browser bundle. | ARC browser manifest і тести збірки. |

Для React можна використати префікс `/api` для бізнес-ендпойнтів. Порівнюємо результати операцій, статуси, помилки, кількість запитів та оновлення UI. Службові маршрути ARC і формат його internal transport є частиною порівняння інструментів. [Курс ARC 0.9](roadmap-0.9.md)
