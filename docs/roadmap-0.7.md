# Курс ARC 0.7

Це робочий стратегічний план наступної серії ітерацій. Версія `0.7.0` — орієнтир, а не обіцянка конкретного набору API. Перед випуском звірити фактичний результат із цим документом і журналом змін.

## Напрям

Зробити шлях від доменної функції до готової сторінки цілісним і коротким: маршрут → контрактні дані → дія → форма та результат. Для інтерфейсу ARC використовує звичний JSX/TSX і подієву модель, а сам зберігає граф залежностей, контракти, межі browser/server і життєвий цикл.

Мета — не розширювати API заради кількості можливостей, а прибирати місця, де типовий сценарій потребує зайвого коду, дублювання понять або ручного з’єднання.

## Принципи рішень

- JSX має залишатися знайомим: HTML-елементи, вирази, умовний вміст, `.map()` із ключем, звичні DOM-події.
- ARC-модель має залишатися явною там, де це важливо для домену: контракти, операції, залежності, межі, scopes і lifecycle.
- Для типового випадку має бути один рекомендований шлях. Низькорівневий API може лишатися для інтеграцій та особливих сценаріїв.
- Не вводити hooks, довільні lifecycle-effects чи окрему модель стану лише для наслідування звичного фреймворку. Реактивність і DOM bindings мають спиратися на граф ARC.
- Автоматично виводити залежності лише там, де їх можна надійно визначити. Явний `needs` кращий за непомітно неповний або хибний граф.
- Кожну зміну перевіряти на реальній наскрізній функції у Workspace, а не лише на ізольованому прикладі API.

## Послідовність ітерацій

### 1. Визначити композицію `component` / `view` / `page`

Звірити фактичні моделі та приклади. Вирішити, що є звичайною функцією JSX для повторного використання, що є вузлом графа ARC, а що є сторінкою маршруту. Усунути найбільш незручну межу композиції, не розмиваючи lifecycle та ownership.

### 2. Узгодити реактивний TSX

Зробити режим reactive JSX передбачуваним у сторінці та її імпортованих модулях. Зменшити ручні залежності для виразів, які компілятор бачить безпечно; для прихованих залежностей залишити зрозумілий явний шлях. Пояснювати помилки та обмеження на етапі збірки.

### 3. Сполучити доменні дані й UI

Пройти повний цикл `contract → query → view → mutation → оновлений query`. Узгодити читання стану, статуси запитів, помилки контракту та оновлення після mutation, щоб одна поведінка не вимагала кількох паралельних API.

### 4. Довести native forms до основного шляху

Зберегти HTML `<form>`, `name` та `onSubmit` як основу. Перевірити, що контракт задає типи й валідацію, форма передає значення, а JSX коротко відображає помилки біля полів. Не дублювати схему поля без реальної потреби.

### 5. Перевірити вертикальну функцію та закріпити API

У Workspace реалізувати або переробити один повний сценарій: список, detail route, створення та редагування. За результатом оновити рекомендований приклад, довідник і changelog; прибрати застарілий рекомендований синтаксис, якщо його замінили.

## Критерії успіху

- Розробник може пройти повний CRUD-сценарій в одному feature-модулі без ручного коду життєвого циклу UI.
- У типовому шляху є по одному очевидному способу описати стан сторінки, контрактний query, mutation, форму та JSX-відображення.
- ARC зберігає коректний граф залежностей і трасу від події користувача до доменної операції та оновлення даних.
- Для типових JSX-читань не потрібні дубльовані оголошення залежностей; коли потрібен явний `needs`, це зрозуміло з коду.
- Скорочення API не створює прихованої поведінки, втрати типів або розбіжностей між графом і runtime.

## Прогрес і наступна задача

**Композицію `component` / `view` / `page` — виконано.** Звичайна функція-компонент повертає TSX-шаблон; оголошений `view` тепер можна вставляти як `<UsersPage />` і він лишається окремим вузлом графа зі своїм mount/lifecycle; route page залишається коренем, який створює маршрутизатор. Workspace переведений на JSX-теги для вкладених view. Збірка перевірена; коміт `ea7d5ac`.

**Реактивний TSX — узгоджено.** ARC CLI тепер вмикає трансформацію на application entry та поширює її на локальний імпортований модульний граф, включно з конфігурацією `web: { nodes, entry }`. Browser build і CLI dev мають один шлях. У графі сторінки звичні виклики джерел і JSX-вирази реактивні без pragma; `// @arc reactive-jsx` лишається для окремого TSX поза application graph. `render`, `each` і `needs` описані як інструменти для явного контролю та прихованих залежностей. Counter тепер показує одноразове обчислення прямо в JSX. Перевірено `npm run typecheck`, `npm run build`, `npm run build:web`; коміт додати після фіксації ітерації.

**Інтеграція доменних записів і UI — триває.** Знайдено дубльовану авторську модель для contract-backed write: `remoteForm` і `mutation` обидва створювали форму, але приклади подавали їх як різні API. `mutation` тепер є рекомендованим способом для форми й прямої дії; `remoteForm` лишився сумісним deprecated API. Оновлено навчальний приклад і довідник. Перевірено `npm run typecheck` та `npm run build:site`.

**Наступна задача цього етапу:** пройти Workspace-цикл `contract → query → view → mutation → оновлений query`, зосередившись на різниці між `refresh` та `update` і на тому, чи можна зробити їхню роль яснішою без об’єднання різних семантик.

- Базовий коміт поточного плану: `c31c1eb` (`Document ARC 0.6 frontend API`).
- Перед стартом перевірити `git status`; на момент запису був наявний сторонній незакомічений стан `D .aws`. Не включати його до змін roadmap і не відновлювати без окремої причини.
- Після кожної завершеної локальної ітерації коротко пояснити зміну та фіксувати її окремим комітом, як домовлено в сесії.
