# Курс ARC 0.7

Це робочий стратегічний план наступної серії ітерацій. Версія `0.7.0` — орієнтир, а не обіцянка конкретного набору API. Перед випуском звірити фактичний результат із цим документом і журналом змін.

## Напрям

Зробити шлях від доменної функції до готової сторінки цілісним і коротким: маршрут → контрактні дані → дія → форма та результат. Для інтерфейсу ARC використовує звичний JSX/TSX і подієву модель, а сам зберігає граф залежностей, контракти, межі browser/server і життєвий цикл.

Мета — не розширювати API заради кількості можливостей, а прибирати місця, де типовий сценарій потребує зайвого коду, дублювання понять або ручного з’єднання.

## Принципи рішень

- JSX має залишатися знайомим: HTML-елементи, вирази, умовний вміст, `.map()` із ключем, звичні DOM-події.
- ARC-модель має залишатися явною там, де це важливо для домену: контракти, операції, залежності, межі, scopes і lifecycle.
- Для типового випадку має бути один рекомендований шлях. Низькорівневий API може лишатися для інтеграцій та особливих сценаріїв.
- Не вводити hooks, довільні lifecycle-effects чи окрему модель стану лише для наслідування звичного фреймворку. Реактивність і DOM bindings мають спиратися на граф ARC.
- Автоматично виводити залежності лише там, де їх можна надійно визначити. Явний `needs` кращий за непомітно неповний або хибний граф.
- Кожну зміну перевіряти на реальній наскрізній функції у Workspace, а не лише на ізольованому прикладі API.

## Послідовність ітерацій

### 1. Визначити композицію `component` / `view` / `page`

Звірити фактичні моделі та приклади. Вирішити, що є звичайною функцією JSX для повторного використання, що є вузлом графа ARC, а що є сторінкою маршруту. Усунути найбільш незручну межу композиції, не розмиваючи lifecycle та ownership.

### 2. Узгодити реактивний TSX

Зробити режим reactive JSX передбачуваним у сторінці та її імпортованих модулях. Зменшити ручні залежності для виразів, які компілятор бачить безпечно; для прихованих залежностей залишити зрозумілий явний шлях. Пояснювати помилки та обмеження на етапі збірки.

### 3. Сполучити доменні дані й UI

Пройти повний цикл `contract → query → view → mutation → оновлений query`. Узгодити читання стану, статуси запитів, помилки контракту та оновлення після mutation, щоб одна поведінка не вимагала кількох паралельних API.

### 4. Довести native forms до основного шляху

Зберегти HTML `<form>`, `name` та `onSubmit` як основу. Перевірити, що контракт задає типи й валідацію, форма передає значення, а JSX коротко відображає помилки біля полів. Не дублювати схему поля без реальної потреби.

### 5. Перевірити вертикальну функцію та закріпити API

У Workspace реалізувати або переробити один повний сценарій: список, detail route, створення та редагування. За результатом оновити рекомендований приклад, довідник і changelog; прибрати застарілий рекомендований синтаксис, якщо його замінили.

## Критерії успіху

- Розробник може пройти повний CRUD-сценарій в одному feature-модулі без ручного коду життєвого циклу UI.
- У типовому шляху є по одному очевидному способу описати стан сторінки, контрактний query, mutation, форму та JSX-відображення.
- ARC зберігає коректний граф залежностей і трасу від події користувача до доменної операції та оновлення даних.
- Для типових JSX-читань не потрібні дубльовані оголошення залежностей; коли потрібен явний `needs`, це зрозуміло з коду.
- Скорочення API не створює прихованої поведінки, втрати типів або розбіжностей між графом і runtime.

## Прогрес і наступна задача

**Композицію `component` / `view` / `page` — виконано.** Звичайна функція-компонент повертає TSX-шаблон; оголошений `view` тепер можна вставляти як `<UsersPage />` і він лишається окремим вузлом графа зі своїм mount/lifecycle; route page залишається коренем, який створює маршрутизатор. Workspace переведений на JSX-теги для вкладених view. Збірка перевірена; коміт `ea7d5ac`.

**Реактивний TSX — узгоджено.** ARC CLI тепер вмикає трансформацію на application entry та поширює її на локальний імпортований модульний граф, включно з конфігурацією `web: { nodes, entry }`. Browser build і CLI dev мають один шлях. У графі сторінки звичні виклики джерел і JSX-вирази реактивні без pragma; `// @arc reactive-jsx` лишається для окремого TSX поза application graph. `render`, `each` і `needs` описані як інструменти для явного контролю та прихованих залежностей. Counter тепер показує одноразове обчислення прямо в JSX. Перевірено `npm run typecheck`, `npm run build`, `npm run build:web`; коміт додати після фіксації ітерації.

**Інтеграцію доменних записів і UI — виконано.** Для contract-backed write `mutation` став єдиним рекомендованим API форм і прямих дій; `remoteForm` лишився сумісним deprecated API. Також уточнено різницю між `refresh` (повторне читання server source of truth) та `update` (застосування повної відповіді до рядка в snapshot/cache). `invalidates` у fullstack mutation позначено deprecated alias до `refresh`. Перевірено `npm run typecheck` та `npm run build:site` на попередній ітерації; поточна зміна пройшла `npm run typecheck`.

**Native forms як основний шлях — виконано.** Перевірено Workspace-сценарії з контрактною валідацією, іменованими полями, двостороннім state і повідомленнями про помилки. Додано `mutation.invalid()` для загальної контрактної помилки, зберігши типізований `mutation.invalid(field)`; приклад більше не перелічує поля для приховування дубльованого загального повідомлення. Підтверджено `npm run typecheck` та `npm run build`.

**Наскрізний CRUD-сценарій — виконано.** Workspace тепер має редагування замовлення на detail-сторінці через контракт `UpdateOrder`, native form і `mutation`. Додано `RemoteResource.replace()` для застосування повної відповіді mutation до query detail без повторного читання; список операцій розширено PUT-маршрутом, а змінене замовлення одразу відображається в актуальному query. Перевірено `npm run typecheck` і `npm run build`.

**Граф динамічних JSX-дій — виправлено.** Посилання на action у JSX-події всередині реактивної гілки тепер стає залежністю render-вузла. Це зберігає remote operation і пов’язаний `UPDATES` зв’язок у графі до того, як query поверне дані й форма з’явиться в DOM. Підтверджено через `npm run typecheck`, `npm run build` і згенерований Workspace graph; коміт `22d924e`.

**Runtime шлях mutation → detail query — підтверджено.** Користувач перевірив Workspace у браузері: замовлення редагується, зміни зберігаються й відображаються на detail-сторінці. Browser service агента при цьому не мав підключеного браузера; локальний dev server користувач відкрив самостійно. Оновлено інструкції Workspace для CRUD і `order.replace()`.

**Рекомендований frontend-шлях — узгоджено.** README та frontend/fullstack/Workspace guides показують один доменний маршрут: контракт → query/mutation → TSX. Документовано повну відповідь для detail query через `replace()` і `running` без окремого локального state. У формах Workspace submit-кнопки блокуються та показують короткий pending-текст. Перевірено `npm run typecheck`, `npm run build`, `npm run build:site` і згенерований graph.

**Валідацію форм звірено.** Контракт залишається остаточним правилом для browser та server; HTML `required`, `min`, `max`, `maxlength` і `type` додають форму вводу й ранні браузерні affordances, а `mutation.invalid(field)` дає сторінці поле для власного повідомлення. Не додавати framework-помічник лише для копіювання schema constraints або доменних текстів у JSX.

**Deprecated frontend API — звірено.** `mutation`/`refresh` — єдиний рекомендований шлях у прикладах. `remoteForm` і fullstack `invalidates` лишаються сумісними deprecated aliases; базовий `action({ invalidates })` не є alias і лишається окремим Web API. Не видаляти сумісні назви в межах 0.7 без окремої міграційної причини. Це розрізнення описано в API та remote operations guide.

**Редагування користувача — реалізовано й підтверджено.** Додано `UpdateUser`, серверну перевірку наявності користувача й унікальності email, PUT-маршрут та форму для вибраного користувача. `UserProfile` задає спільні поля create/update/output без повтору schema rules. `update: users.replaceBy("id")` синхронізує рядок і похідний активний користувач без повторного читання. Користувач підтвердив, що UI працює. Graph містить mutation та remote boundary; перевірено `npm run typecheck` і `npm run build`.

**Кілька query-цілей однієї mutation — додано.** `update` тепер приймає масив стратегій з однаковим типом відповіді й застосовує їх в одному batch. Редагування замовлення синхронізує detail і список через `order.replace()` та `ordersData.replaceBy("id")`, без додаткового GET. Graph показує обидва `UPDATES` ребра. Перевірено типізацію, збірку та IR.

**Наступний крок — перевірити свіжість списку після редагування замовлення.** Після зміни назви або кількості повернутися до `/orders` і переконатися, що рядок та підсумок оновилися без ручного перезавантаження. Якщо query lifetime чи navigation cache цьому заважає, виправити відповідний lifecycle.
